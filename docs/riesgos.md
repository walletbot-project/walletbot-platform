# Registro de riesgos

Actualizado: 2026-08-07

Este documento mantiene los riesgos actuales del proyecto en un formato liviano.
La idea es revisarlo al cierre de cada iteración o cuando una decisión técnica
cambie la probabilidad, el impacto o la mitigación de un riesgo.

## Criterios

- Probabilidad: Baja, Media, Alta.
- Impacto: Bajo, Medio, Alto, Crítico.
- ID: identificador estable para referenciar riesgos en issues, PRs o reuniones.
- Prioridad: orden relativo de importancia actual; puede cambiar sin cambiar el
  ID del riesgo.
- Mantener cada mitigación como una acción concreta y verificable.
- Si un riesgo deja de aplicar, moverlo a una sección de riesgos cerrados en
  lugar de borrarlo.

| 6 | R-002 | Se exponen datos financieros personales por errores de autorización, logging o configuración de entorno. | Seguridad / Privacidad | Baja | Crítico | Requiere más análisis específico de privacidad y seguridad; mientras tanto, derivar siempre el usuario desde la sesión server-side y evitar logs con datos financieros sensibles. | 7 | R-004 | La app web y la app nativa divergen en experiencia de usuario. | UX | Media | Bajo | Definir criterios compartidos para los flujos principales y revisar paridad visual y funcional en cada feature que toque movimientos, cuentas o categorías. Paridad cerrada (2026-08-06): el detalle de actividad web ahora muestra el saldo de la cuenta antes/después de la transacción, como el nativo (`v1/transactions/queries:balanceAroundTransaction`). Paridad cerrada (2026-08-07): la web pasa a ser bilingüe es/en con selector de idioma tri-estado (`system`/`es`/`en`) persistido por dispositivo, igual que el nativo; antes era español con textos sueltos en inglés. Divergencia activa nueva: los catálogos son independientes por decisión de producto (nativo usa ARB en `apps/native/lib/l10n/`, web usa `apps/web/src/lib/i18n/{es,en}.ts`), así que el wording puede divergir entre plataformas aunque ambas soporten los mismos idiomas; revisar copy de ambos lados en features que toquen movimientos, cuentas o categorías. |
| 8 | R-008 | Un write path nuevo en la app nativa escribe a la base local sin respetar el contrato de sync (`dirty`/`updatedAt`/tombstones) y los cambios no sincronizan o se pierden por LWW. | Técnico / Sync | Baja | Alto | Mantener todas las escrituras detrás de `lib/data/` (refactor 2026-06-11): repositorios con contrato único, tests unitarios del contrato (`test/data/`), CI de analyze+test para la app nativa y gate de revisión "ningún `db.into/update/delete` fuera de `lib/data/` y `lib/sync/`". Las nuevas tablas `savedFilters`/`dashboardWidgets` (home dashboard) siguen el mismo contrato vía `SavedFilterRepository`/`DashboardRepository` y están cubiertas por `write_contract_test.dart`. Gate de versión de cliente aplicado en **ambos lados**: además del gate cliente (`_SyncStarter` lee `syncAllowed`), `v1/sync/mutations:push` y `v1/sync/queries:pull` validan `appVersion`/`platform` contra `minSupportedVersion` en el servidor (`config/helpers.ts:isClientSupported`) y devuelven `{ ok: false, error: 'client_outdated' }`; el motor de sync se detiene y el cliente pasa al aviso de actualización obligatoria. Así un cliente viejo o manipulado que falla/omite el fetch de config (y queda fail-open) igual no puede sincronizar un wire incompatible. |
| 9 | R-009 | Un cambio de schema SQLite rompe instalaciones existentes o pierde datos locales durante la migración. | Técnico / Persistencia | Media | Alto | Baseline nativo coordinado en `v1`; desde ahí, generar artefactos con `drift_dev make-migrations`, implementar `onUpgrade` explícito y data-preserving para cada versión soportada, cubrir migraciones con tests de schema e integridad, y coordinar resets locales cuando una versión previa no sea soportada. |
| 10 | R-010 | Una URL de backend fija embebida en la app nativa deja inutilizables las instalaciones existentes si el deployment de Convex cambia (plan gratuito, sin dominio propio para el backend). | Técnico / Operaciones | Baja | Alto | Capa de bootstrap L0: la app resuelve la URL del backend desde un JSON estático estable (`BOOTSTRAP_URL`) al iniciar, con fallback a la caché del último valor bueno y luego al valor embebido (falla abierta, no bloquea el arranque). Las URLs recibidas se validan como `https` con host no vacío antes de aplicarse o cachearse, para que una respuesta comprometida/MITM no pueda redirigir el WebSocket ni los POST de `/auth/refresh` (que llevan el token de sesión) a otro host. Ver `apps/native/lib/app_config/bootstrap.dart`. |
| 11 | R-011 | El endpoint `POST /telemetry/metrics` acepta métricas sin autenticación y puede recibir contadores de negocio falsos o inflados desde clientes externos. | Observabilidad / Integridad de datos | Media | Medio | Riesgo aceptado temporalmente para mantener pruebas manuales flexibles desde Bruno sin token. Mantener catálogo y validación de labels de baja cardinalidad, no enviar PII ni datos financieros, usar estas métricas como señal direccional durante MVP y revisar antes de usar dashboards para decisiones de negocio o reporting externo. |
| 12 | R-012 | `v1/transactions/queries:balanceAroundTransaction` hace `.collect()` sobre las transacciones que comparten la fecha exacta de la transacción objetivo (índices `by_user_account_date` y `by_user_to_account_date`) para romper empates alrededor del saldo. Es una lectura sin cota: un import masivo o una normalización que lleve muchas transacciones de una misma cuenta al mismo milisegundo podría superar los límites por query de Convex (~32k documentos escaneados / 16 MiB) y hacer que la query falle en vez de devolver el saldo. | Técnico / Rendimiento | Baja | Medio | Riesgo aceptado por ahora (detectado en review de Macroscope, PR #178). El set de empates está acotado a (usuario, cuenta, milisegundo exacto), por lo que en uso normal se mantiene chico, y el guard de `parseTransactionDate` evita colapsar movimientos a medianoche al crearlos con hora conocida. Antes de habilitar imports masivos o backfills que normalicen fechas, acotar el tie-break con `.take(N)` + `log` de truncamiento, o plegar los desempates (`createdAt`/`id`) en un rango index-backed para que la lectura quede acotada. Ver `packages/backend/convex/v1/transactions/queries.ts`. |

| 15 | R-015 | El reset de contraseña crea una credencial de password en cuentas que eran sólo-Google (comportamiento de better-auth cuando no existe cuenta `credential`), habilitando un vector de login adicional no solicitado. | Seguridad / Auth | Baja | Medio | Aceptado: el flujo exige posesión del email (enlace de reset de un solo uso, vence en 1 hora) y el hint de la pantalla de login sigue empujando a Google. | 16 | R-016 | La eliminación de cuenta por enlace de email (2026-08-06) borra datos financieros de forma irreversible: un buzón comprometido alcanza para destruir la cuenta, y un fallo a mitad del purge por lotes podría dejar datos parciales o al usuario de better-auth sin borrar. | Seguridad / Producto | Baja | Alto | Fricción deliberada: enlace de un solo uso (hash SHA-256 en `userDeletionRequests`, vence en 24 h, máx. 3 pedidos por hora por email, anti-enumeración), página de confirmación que exige tipear "ELIMINAR" y advierte la irreversibilidad, y email con la misma advertencia. Al confirmar, el usuario entra en la denylist `deletedUsers` — `requireAuth` rechaza sus JWTs stateless aún válidos (nativos duran 24 h), evitando que un dispositivo offline re-sincronice datos después del purge — y se revocan sesiones web y tokens nativos. El purge (`userDeletion/internal.ts:purgeUserData`) es idempotente y por lotes (patrón backfill); si la cadena muere, reabrir el enlace la re-agenda. Agregados de transacciones actualizados por documento (`deleteIfExists`), nunca `clear()` sobre el namespace compartido `__none__`. Si se agrega 2FA, el confirm debe exigir el segundo factor antes de consumir el token. |
