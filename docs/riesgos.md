# Registro de riesgos

Actualizado: 2026-09-30

Este documento mantiene los riesgos actuales del proyecto en un formato liviano.
La idea es revisarlo al cierre de cada iteración o cuando una decisión técnica
cambie la probabilidad, el impacto o la mitigación de un riesgo.

## Criterios

- Probabilidad: Baja, Media, Alta.
- Impacto: Bajo, Medio, Alto, Crítico.
- ID: identificador estable para referenciar riesgos en issues, PRs o reuniones.
- Prioridad: orden relativo de importancia actual; puede cambiar sin cambiar el
  ID del riesgo.
- Mantener cada mitigación como una acción concreta y verificable.
- Si un riesgo deja de aplicar, moverlo a una sección de riesgos cerrados en
  lugar de borrarlo.

Voz — reconexión (2026-08-17): los tokens efímeros de Gemini Live son de un solo uso (`uses: 1`); el cliente nativo cacheaba el token ~20 h y lo re-presentaba en cada reconexión (goAway periódico, cortes de red, background), dejando la sesión en un loop de backoff permanente. Ahora cada intento de conexión resuelve un token fresco, el mint fija `newSessionExpireTime` explícito (2 min), y cada fase de conexión se persiste en el event log (`connection_phase: {phase, elapsedMs}`) para que una conexión lenta o un loop de reconexión sean diagnosticables desde una sesión exportada. Voz — cortes y envíos offline (2026-08-21): un intento de conexión fallido ya no finaliza la sesión registrada (antes un envío de texto sin red marcaba la conversación como terminada, destruyendo el contexto reanudable); los mensajes tipeados durante un corte se encolan y se envían en orden al reconectar, y los errores crudos ya no se muestran en el chat (quedan en el log de sesión y la consola de debug) — el botón de finalizar es la única salida explícita de una conversación. La continuidad del contexto del modelo ya no depende de los resume handles de Gemini: verificado contra la API en vivo (2026-08-21), un handle deja de resumir a los pocos segundos de un corte abrupto (modo avión, background) y el server abre silenciosamente una sesión EN BLANCO; ahora cada conexión re-siembra el contexto desde el transcript del log local (`buildConversationSeed`), así el contexto del modelo siempre coincide con lo que la UI muestra. El mic en Android ya no muere tras una notificación: el plugin `record` pausa la captura ante cualquier pérdida de foco de audio y su default nunca la reanuda (`audioInterruption: pauseResume`).. Nueva dependencia `sign_in_with_apple` (2026-09-06) fijada con techo explícito `>=8.1.0 <8.2.0`: 8.2.0 exige Dart ^3.12.0 / Flutter >=3.44.0 y CI pinea Flutter 3.41.6, así que un rango caret resuelve distinto en la máquina de desarrollo (Dart 3.12.2) que en el runner y rompe sólo en CI. Levantar el techo y el pin de CI juntos. |
| 7 | R-002 | Se exponen datos financieros personales por errores de autorización, logging o configuración de entorno. | Seguridad / Privacidad | Baja | Crítico | Requiere más análisis específico de privacidad y seguridad; mientras tanto, derivar siempre el usuario desde la sesión server-side y evitar logs con datos financieros sensibles. Telemetría v1 acepta eventos genéricos con tamaño acotado, usuario derivado server-side cuando hay auth y contrato explícito de no enviar PII ni datos financieros en `properties`. El JSON de debug de function calls del bot de voz (args/resultados de tools, potencialmente con montos y descripciones) se mostraba siempre en prod en nativo y web; ahora queda detrás del feature flag `debugToolCalls`, apagado por default y sólo habilitable por usuario desde un dashboard admin-only (`ctx.db` `admins` table + `requireAdmin` server-side en cada query/mutation, ver `packages/backend/convex/v1/featureFlags/`). Mitigación reforzada (2026-08-05): verificación de email obligatoria (`requireEmailVerification`) impide registrar cuentas con correos ajenos, y el reset de contraseña revoca todas las sesiones (web vía `revokeSessionsOnPasswordReset`, nativas vía `revokeAllSessionTokensForUser`), cortando el acceso de un dispositivo comprometido. Los endpoints de forgot/resend tienen rate limit server-side (`storage: 'database'`) y hasta 2026-08-21 tampoco revelaban si un email existía (anti-enumeración); ver la decisión ampliada más abajo. Excepción deliberada (2026-08-14): `/auth/email/sign-up` **sí** responde `409 account_exists` cuando la dirección ya está registrada. Antes devolvía el usuario sintético de better-auth (`token: null`, indistinguible de un alta real) y el cliente mostraba "te enviamos un enlace de verificación" para un correo que nunca se enviaba, dejando sin salida a las cuentas creadas con Google (ver R-017). El 409 no dice **qué** proveedor usa la cuenta —puede tener contraseña y social a la vez—, así que sólo revela que la dirección está tomada, lo mismo que ya revela cualquier alta al fallar. Un alta repetida sobre una cuenta con contraseña sin verificar no devuelve 409: reenvía el enlace (con rate limit por dirección) y mantiene el flujo de verificación pendiente. Decisión ampliada (2026-08-21): la excepción de sign-up pasó a ser la regla en **todos** los endpoints que mandan mail, porque la opacidad hacía que la app mintiera. `/auth/password/forgot`, `/auth/email/resend-verification` y `/v1/account-deletion/request` resolvían la dirección con better-auth (o con `createRequest`), que responde éxito sin invocar el hook de envío, y devolvían `{ ok: true }` para una dirección inexistente, un correo ya verificado, un pedido throttleado, una cuenta ya eliminada y un fallo real de Resend — indistinguibles de un envío real, así que la UI mostraba "te enviamos un enlace" para correos que nunca salieron. Ahora los tres buscan la dirección primero y `{ ok: true }` significa una sola cosa: el mail se entregó a Resend. Todo lo demás tiene su propio código (`account_not_found` 404, `email_already_verified` 409, `account_already_deleted` 410, `rate_limited` 429, `email_send_failed` 500) y cada cliente lo nombra. La contrapartida aceptada es que un llamador anónimo puede enumerar direcciones registradas en esos tres endpoints; sigue acotada por el rate limit por dirección (que se descuenta **antes** del lookup, así que sondear cuesta un slot) y no expone nada más que la existencia de la cuenta —nunca el proveedor—. En la web esto además saca a `authClient.signUp.email`, `authClient.requestPasswordReset` y `authClient.sendVerificationEmail` del camino: los cuatro flujos pasan por los endpoints propios del backend, los mismos que usa el nativo. Superficie nueva (2026-08-19): la web pasó a replicar el historial de voz a `voiceSessions`/`voiceSessionEvents` (`apps/web/src/lib/voice-history.ts`), así que las transcripciones y los argumentos/resultados de tools —que pueden traer montos y descripciones— ahora se persisten server-side también desde el navegador, no sólo desde el nativo. No agrega una clase de dato nueva a la base (el nativo ya la escribía) pero sí más usuarios y más sesiones: el cron de retención de voz de 12 meses que el texto legal promete (ver R-013) ahora aplica a las sesiones web y sigue sin implementarse, y no hay endpoint de export server-side, así que la copia de un usuario web vive únicamente en Convex. El `ownerId` que manda el cliente se valida contra la identidad autenticada y la mutación rechaza el desajuste; los bytes de audio no salen del cliente en ninguna plataforma. |
