# Registro de riesgos

Actualizado: 2026-08-05

Este documento mantiene los riesgos actuales del proyecto en un formato liviano.
La idea es revisarlo al cierre de cada iteración o cuando una decisión técnica
cambie la probabilidad, el impacto o la mitigación de un riesgo.

## Criterios

- Probabilidad: Baja, Media, Alta.
- Impacto: Bajo, Medio, Alto, Crítico.
- ID: identificador estable para referenciar riesgos en issues, PRs o reuniones.
- Prioridad: orden relativo de importancia actual; puede cambiar sin cambiar el
  ID del riesgo.
- Mantener cada mitigación como una acción concreta y verificable.
- Si un riesgo deja de aplicar, moverlo a una sección de riesgos cerrados en
  lugar de borrarlo.

| 6 | R-002 | Se exponen datos financieros personales por errores de autorización, logging o configuración de entorno. | Seguridad / Privacidad | Baja | Crítico | Requiere más análisis específico de privacidad y seguridad; mientras tanto, derivar siempre el usuario desde la sesión server-side y evitar logs con datos financieros sensibles. Mitigación reforzada (2026-08-05): verificación de email obligatoria (`requireEmailVerification`) impide registrar cuentas con correos ajenos, y el reset de contraseña revoca todas las sesiones (web vía `revokeSessionsOnPasswordReset`, nativas vía `revokeAllSessionTokensForUser`), cortando el acceso de un dispositivo comprometido. | 7 | R-004 | La app web y la app nativa divergen en experiencia de usuario. | UX | Media | Bajo | Definir criterios compartidos para los flujos principales y revisar paridad visual y funcional en cada feature que toque movimientos, cuentas o categorías. | 8 | R-008 | Un write path nuevo en la app nativa escribe a la base local sin respetar el contrato de sync (`dirty`/`updatedAt`/tombstones) y los cambios no sincronizan o se pierden por LWW. | Técnico / Sync | Baja | Alto | Mantener todas las escrituras detrás de `lib/data/` (refactor 2026-06-11): repositorios con contrato único, tests unitarios del contrato (`test/data/`), CI de analyze+test para la app nativa y gate de revisión "ningún `db.into/update/delete` fuera de `lib/data/` y `lib/sync/`". Así un cliente viejo o manipulado que falla/omite el fetch de config (y queda fail-open) igual no puede sincronizar un wire incompatible. |
| 9 | R-009 | Un cambio de schema SQLite rompe instalaciones existentes o pierde datos locales durante la migración. | Técnico / Persistencia | Media | Alto | Baseline nativo coordinado en `v1`; desde ahí, generar artefactos con `drift_dev make-migrations`, implementar `onUpgrade` explícito y data-preserving para cada versión soportada, cubrir migraciones con tests de schema e integridad, y coordinar resets locales cuando una versión previa no sea soportada. |
| 10 | R-010 | Una URL de backend fija embebida en la app nativa deja inutilizables las instalaciones existentes si el deployment de Convex cambia (plan gratuito, sin dominio propio para el backend). | Técnico / Operaciones | Baja | Alto | Capa de bootstrap L0: la app resuelve la URL del backend desde un JSON estático estable (`BOOTSTRAP_URL`) al iniciar, con fallback a la caché del último valor bueno y luego al valor embebido (falla abierta, no bloquea el arranque). Las URLs recibidas se validan como `https` con host no vacío antes de aplicarse o cachearse, para que una respuesta comprometida/MITM no pueda redirigir el WebSocket ni los POST de `/auth/refresh` (que llevan el token de sesión) a otro host.
